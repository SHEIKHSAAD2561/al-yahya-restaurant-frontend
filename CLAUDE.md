## Project

Admin console for Al-Yahya Restaurant — single-tenant (one restaurant, not multi-tenant SaaS), bilingual (English/Arabic with RTL). Talks to a sibling NestJS backend at `../al-yahya-restaurant-backend` (not part of this repo; see that repo's own CLAUDE.md). Only Auth, Products (Phase 1), Category Management, Customers, Customer Payments (+ Sell Screen "Pay Later" checkout — see below), POS (Registers + Sell Screen + Invoice List + Cash Management + printable receipts — see below), Sale Settings (Sales + Receipts tabs only), Sale Invoices, Promotions (catalog/scheduling only, not enforced at checkout — see below), Expenses, Home/Dashboard, Reports, Purchases & Suppliers (Suppliers/Purchase Invoices/Return Invoices/Supplier Payments — see below), Stock (Operations/Count/Transfer — see below), Accounting (Chart of Accounts/Journal Entries/Fixed Assets/Financial Reports/Setup Guide — manual double-entry, not auto-posted from other modules, see below), Digital Menu (a public, unauthenticated `/menu` page generated from existing Products/Categories, plus an internal `/digital-menu` admin preview — see below), and Settings → Company Overview/Users/Roles & Permissions/Locations/Taxes/Configuration/Payment Methods are real, fully-wired features today — everything else in the sidebar (Sale Settings' Selling Screen/eCommerce Orders tabs, Modifiers, eCommerce Orders) and the remaining Settings tabs shown in Rewaa references (Custom Fields, Import Logs, Finance) are permission-gated "coming soon" stubs or simply not built yet, because the backend has no real endpoints for those.

## Commands

Run from the project root. The backend must also be running (`npm run start:dev` in `../al-yahya-restaurant-backend`, port 3001) for anything beyond the login screen to work.

- `npm run dev` — dev server with Turbopack (http://localhost:3000)
- `npm run build` — production build (also type-checks)
- `npm run start` — serve the production build (never use this while actively developing — it doesn't hot-reload; use `dev`)
- `npm run lint` — ESLint (flat config, includes React Compiler-aware hooks rules)

`.env.local` needs `BACKEND_URL` (the NestJS API origin) and `SESSION_SECRET` (signs this app's own session cookie — generate with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`). No test runner configured yet.

## Architecture

Next.js 16 App Router, React 19, TypeScript strict, Tailwind v4. Path alias `@/*` → `src/*`.

### Directory layout (feature-sliced)

- `src/app/` — routing only, kept thin. `[locale]/(auth)/*` (login, accept-invitation, forgot-password) and `[locale]/(dashboard)/*` (everything behind auth) are separate route groups with separate layouts. `app/api/**` holds the BFF Route Handlers (see Auth below) — the only files allowed to touch the backend's raw JWTs.
- `src/core/` — cross-cutting, not domain-specific: `auth/` (session/cookie machinery), `permissions/` (codes + client-side gating), `i18n/` (next-intl config), `api/` (fetch clients, TanStack Query setup), `nav/` (`nav-config.ts` — the single source of truth for sidebar items *and* their required permission codes), `company/` (`get-company-branding.ts` — server-only, hits the backend's public branding endpoint directly, a deliberate narrow exception to the "only Route Handlers touch the backend" rule since it needs no cookies), `phone/` (`country-codes.ts` — shared country-code list + phone split/join helpers), `config/env.ts`.
- `src/features/<name>/` — one per domain (`auth`, `users`, `roles`, `permissions`, `locations`, `company`, `taxes`, `configuration`, `payment-methods`, `products`, `categories`, `brands`, `registers`, `customers`, `sales`), each with `api/` (fetch functions + query-key factories), `components/`, `hooks/` (TanStack Query wrappers), `schemas/` (zod), `types/`.
- `src/components/ui/` — Radix primitives + Tailwind, shadcn-style (the component code is owned/edited directly, not an installed package). `src/components/layout/` — shell chrome (Sidebar, Topbar, Sheet-based settings tabs, etc).
- `src/proxy.ts` — Next 16 renamed `middleware.ts` to `proxy.ts`; don't recreate a `middleware.ts`, it won't run.

### Auth: BFF pattern, httpOnly cookies

The backend issues its own access/refresh JWTs, but the browser **never sees them**. Three httpOnly cookies (`src/core/auth/cookies.ts`):
- `access_token` / `refresh_token` — the backend's raw tokens, forwarded server-side only.
- `session` — a **separate**, compact JWT this app signs itself (`jose`, `src/core/auth/jwt-session.ts`) from the backend's `GET /auth/me` response, carrying `{sub, nameEn, nameAr, email, roleId, roleType, permissionCodes, preferredLanguage}`. This exists because the backend's access token payload is only `{sub}` — no role/permission data — so `proxy.ts` and server components need something they can read synchronously without a network call.

Route Handlers own all cookie writes: `app/api/auth/{login,logout,accept-invitation,forgot-password}/route.ts` for the auth-establishing calls, and a single catch-all `app/api/backend/[...path]/route.ts` for every other authenticated backend call (users/roles/permissions/locations) — it attaches `Authorization: Bearer <access_token>` + `x-lang: <locale>`, and on a `401` does one silent refresh (mints a fresh `session` too) before retrying. Feature code never imports fetch logic that hits the backend directly — always through `core/api/backend-fetch-client.ts` (browser) which calls the catch-all, or `core/api/backend-fetch-server.ts` (server-only, used only inside Route Handlers).

**Known tradeoff**: since `permissionCodes` is baked into the `session` cookie at login/refresh time, a role's permissions changing does *not* take effect for an already-logged-in user until their session cookie naturally re-mints (≤15 min, tied to the backend's access-token TTL) or they log out/in. This is expected, not a bug.

### Permissions

`src/core/permissions/codes.ts` (`PERMISSIONS`, `PERMISSION_MODULES`) is hand-synced to the backend's `permission-catalog.ts` — keep them in step when that changes. Gating happens in three places for three different needs:
- `proxy.ts` — coarse only (is there a valid session). Deliberately does *not* do fine-grained permission checks (Next's own guidance: proxy should stay coarse; every page re-verifies). The one exception is `/settings` itself, which has no page and must permission-aware-redirect to whichever tab (from `SETTINGS_TABS` in `nav-config.ts`) the user actually has — that logic has to live in proxy (not a page's `redirect()`) so it resolves before any page renders.
- `core/auth/permissions.ts` → `requirePermission()` — server-side, called at the top of protected pages, redirects home if missing.
- `core/permissions/session-context.tsx` → `usePermission()`/`useSession()` — client-side, reads from a `<SessionProvider>` seeded once in `(dashboard)/layout.tsx`, for conditionally rendering UI (buttons, menu items).

A user has **exactly one role** (`roleId`, not an array) — this is intentional, not a limitation to work around. "Assign to Users" (Roles & Permissions) *reassigns* a user's role; it does not add a second one.

### i18n / RTL

`next-intl`, locale-prefixed routing (`/en/...`, `/ar/...`), messages in `src/messages/{en,ar}.json`. `directionForLocale()` in `core/i18n/routing.ts` drives `<html dir>` in the root `[locale]/layout.tsx`. Use logical Tailwind properties (`ps-`/`pe-`/`start-`/`end-`, not `pl-`/`pr-`/`left-`/`right-`) in any new UI so it mirrors correctly in Arabic.

### Data layer

TanStack Query. Each feature's `api/*.query-keys.ts` exports a keys factory (`{all, lists, list(filters), details, detail(id)}` convention); mutations invalidate via `queryClient.invalidateQueries({queryKey: xKeys.lists()})` and toast (`sonner`) on success/error — `ApiError.message` from the backend is already localized (the fetch clients forward the active locale as `x-lang`/`x-locale`), so error toasts just show it directly.

### Naming quirk to know about

Both `User` and `Role` have bilingual `nameEn`/`nameAr` fields, not a single `name` — display code picks one based on `useLocale()`/`getLocale()`. `Location` has a single `name` (not bilingual) plus an `isDefault` flag (exactly one location can be default; used to pre-select a location for new users). `Role` also has an optional bilingual `description`/`descriptionEn`/`descriptionAr` (backend localizes it into one `description` string, same as `name`).

### React Compiler + react-hook-form gotcha (real bug, hit repeatedly — read before writing any form)

**Never populate a `Controller`-bound field via `reset()` inside a `useEffect` that fires after data loads.** This app's React Compiler setup does not reliably re-render a `Controller`'s subscribed field when `reset()` is called from an effect — a `<Select>`/`<Checkbox>` driven through `Controller` can silently keep showing its stale/empty value even though `useForm`'s internal state (and the raw query data) is correct. Plain `register()`-bound `<input>`s are *not* affected (react-hook-form writes those straight to the DOM node), which is why this bug is easy to miss — some fields on a form update correctly while a `Controller`-bound one next to it doesn't.

The fix used everywhere in this codebase (`company-overview-page.tsx`, `tax-form-page.tsx`, `user-drawer-form.tsx`): split into an outer component that fetches/loads the data and an inner form component that receives the loaded record as a **prop**, keyed by something that changes on every real update (`key={record.updatedAt}` or `key={record?.id ?? 'new'}`). The inner form builds `useForm`'s `defaultValues` directly from that prop — no `reset()`, no effect. A fresh save (new `updatedAt`) or a different target (new `id`) naturally remounts the form with correct values. Do this for any new form that edits existing data; don't reach for `reset()`-in-`useEffect` even though it's the "obvious" pattern from react-hook-form's own docs.

Separately: `useWatch({control, name})` does *not* have this problem (used safely for live derived values, e.g. the Tax form's Total Rate) — it's specifically `Controller` + a value set via `reset()` after mount that's unreliable.

### Radix `<Select>` gotcha: pre-filled value shows blank

A Radix `<Select value={x}>` only auto-displays the matching `<SelectItem>`'s text if that item has actually rendered at least once — which only happens while the dropdown is open (`SelectContent` unmounts while closed). A value set programmatically (from `defaultValues`, not a user click) can render **blank** on first paint even though `value` is non-empty. Fix: pass explicit `children` to `<SelectValue>` instead of relying on the default behavior — `<SelectValue>{value ? label(value) : undefined}</SelectValue>`. See `company-overview-page.tsx`'s Business Type select or `user-filters-bar.tsx` for the pattern.

### Company branding: public endpoint + dynamic favicon

`src/core/company/get-company-branding.ts` hits the backend's `GET /company/branding` (public, no permission gate — see that repo's CLAUDE.md) and is called from both dashboard/auth layouts (to brand the sidebar/login logo via `BrandMark`) and `src/app/icon.tsx` (a code-generated favicon route that fetches and streams back the actual logo image, falling back to `src/app/default-favicon.ico` when none is set). `src/app/icon.tsx` must stay excluded from `proxy.ts`'s matcher (alongside `favicon.ico`) — browsers request the tab icon with no session, and the auth-gating logic would otherwise redirect it to `/login`.

### Taxes: system vs. custom, locked vs. toggleable

Mirrors the backend's `Tax.type` model (`SYSTEM_LOCKED | SYSTEM_TOGGLABLE | CUSTOM`, `src/features/taxes/types/tax-type.ts`). `taxes-page.tsx`'s action column branches on it: `CUSTOM` gets an edit pencil (no activate/deactivate — custom taxes are always active), `SYSTEM_LOCKED` gets a disabled "Activated" pill, `SYSTEM_TOGGLABLE` gets a real Activate/Deactivate button behind a confirmation dialog (`ToggleTaxStatusDialog`). `tax-form-page.tsx` renders fully read-only (disabled inputs, no Save button) for anything non-`CUSTOM` — don't remove that guard even though the backend also rejects the edit, since the point is to not show an editable-looking form for something the API will 403 on save.

### Phone input: country code + number

`src/core/phone/country-codes.ts` exports `COUNTRY_CODES` (Gulf countries first, default `+966`), `splitPhoneNumber()`/`joinPhoneNumber()`. The backend's `User.phone` is one plain string — the split only exists in the UI (`user-drawer-form.tsx`'s `phoneCountryCode`/`phoneNumber` form fields, joined on submit). `splitPhoneNumber()` falls back to `+966` + the raw value verbatim for any legacy/unrecognized value rather than guessing a wrong country.

### Configuration: per-card saves, tobacco tax locks sell tax status

`features/configuration/` — each card (Tax, Location, Weighted Product, Shipping, Payment) is its own form with its own `PATCH /configuration/<section>`, all behind `settings.financial_settings`. Each card is keyed by its *own* saved values in `configuration-page.tsx` (same keyed-remount rule as above), so an outside change (e.g. activating a tax on the Taxes tab) remounts only that card. Rules: the Default Tax dropdown lists only **active** taxes (so "VAT + Tobacco Tax" appears only once activated); while it's active, the backend returns `sellTaxStatusLocked: true` and Sell Tax Status is fixed to Exclusive (disabled here, enforced in the backend too). Cost Tax Status is always Exclusive (read-only). Default Location is `Location.isDefault`, not a separate setting — the options come from the narrow `GET /configuration/location-options` so this page doesn't need `settings.locations.manage`. Tax-status, location, and payment-method mutations also invalidate `configurationKeys.all`. Default Payment Method is a row id from Payment Methods (not an enum). The "Edit Products Quantity" card is display-only.

### Payment Methods: inline rows, bank accounts as "Linked Account"

`features/payment-methods/` — Rewaa-style table with **inline** add/edit rows (`payment-method-row-form.tsx`, a `<tr>` so no `<form>`: ✓/Enter submit via `handleSubmit`), not a drawer. The add row replaces the filter row while open; an edit row is keyed `${id}|${updatedAt}` (keyed-remount rule). Filtering and pagination are client-side (`components/ui/table-pagination.tsx`, shared with Taxes). Type `CASH` has no linked account; every other type requires one — "Linked Account" is a **bank account** (`GET/POST /bank-accounts`, the "Add New Bank" dialog), not a chart-of-accounts entry (no accounting module yet). Built-in rows (`systemCode` set: Cash, Credit Card) can be renamed/relinked but their type is locked. No delete (sales will reference them). All behind `settings.financial_settings`.

### Products (Phase 1): variants are the unit, permissions trim fields

`features/products/`. A product is a *main product* with one or more **variants** — SIMPLE/COMPOSITE have exactly one, VARIABLE one per option combination — and the list (`GET /products`, server-side paginated) returns **variant rows** (hence its "Main Product" column). Per-location pricing/tax/stock lives on each variant (`variants[].locations[]`). Routes: `/products` (`products.access`), `/products/new` (+`products.create`), `/products/[id]` read-only view, `/products/[id]/edit` (+`products.edit`); delete needs `products.delete`.

One `ProductForm` (`product-form.tsx`) serves all 3 types × create/edit/view; view mode is a `<fieldset disabled>`. `ProductFormPage` loads form options/categories/brands/product first, then mounts the form keyed (`id|updatedAt`, or `type|counter` for new — switching type or "Save and New" remounts). Numeric inputs are strings in form state; `utils/product-form-values.ts` builds defaults from props and converts to the API payload. VARIABLE variants are re-derived from options in event handlers (`syncVariantsWithOptions`, keeps surviving combinations' ids/SKUs/prices) — no effects.

Field visibility mirrors the backend, which **omits** fields the caller can't see: cost & buy price need `products.view_cost`; quantities need `stock.access` (and only for the user's assigned locations). Initial quantity and initial cost are enterable **only for a not-yet-saved variant** — afterwards stock operations/purchases own them, and the backend ignores them on edit. Composite cost and "max to sell" are derived server-side from components. The form reads locations/active taxes/default tax/tax-inclusive status/shipping units from `GET /products/form-options` (narrow projection — no `settings.*` permission needed). Categories (`features/categories`, create needs `products.manage_categories`) and brands (`features/brands`, create needs `products.create` or `products.edit`) are created inline via the Classification "+".

Not built yet (deliberately — depend on missing modules): Produced item source/recipes (needs units of measure), supplier, custom fields, modifiers, packs, batch/serial tracking, stock adjustment (belongs to the not-yet-built Stock module), print barcode, column customisation.

### Category Management: hierarchical, up to 3 levels, product assignment

`features/category-management/` (route `/category-management`, `products.manage_categories`) replaces the old flat category picker with a real tree: parent → child → sub-child, no deeper (`MAX_CATEGORY_DEPTH` in both `features/categories/types/category.ts` and the backend). `GET /categories` (`features/categories/`) now returns each category's `parentId`, `depth`, and `productCount`, flat — `utils/category-tree.ts`'s `buildCategoryTree()` nests it client-side for the sidebar, and `categoryPath()` builds a "Parent / Child" label reused by the product form's Classification dropdown (`classification-section.tsx`) so same-named categories under different parents stay distinguishable.

Two creation flows, both from `new-category-dialog.tsx`'s choice step: **Individual category** (`individual-category-form.tsx`, name + description + an optional single parent via a toggle) and **Category tree** (`category-tree-form.tsx`, a fixed 3-level builder — parent/child/sub-child, not a generic depth-N tree, matching what the dialog's own "+ Add child category" / "+ Add sub-child" buttons actually offer — with a live nested-box preview). The parent-category field in the tree flow is a plain `<input list>` (native HTML datalist) suggesting existing top-level names, not a custom combobox component — typing an unlisted name creates a new top-level category, matching one already there extends it.

Category Management's right panel reuses `useProductsQuery()` (the same hook and endpoint the main Products list uses) — its category-scoped view just adds `categoryId` or the new `uncategorized: true` param (`QueryProductsDto.uncategorized` on the backend, mutually exclusive with `categoryId`) — then groups the variant-level rows back into one row per product client-side (`utils/group-products.ts`), since this view is product-level, not variant-level, unlike the main list. Capped at 100 results (the backend's own pageSize ceiling) with a "showing first 100 of N" note rather than pagination — a deliberate v1 simplification for what's expected to be a low-traffic admin screen. A product with more than one variant shows only its first variant's SKU plus a "+N" count, not an expandable per-variant sub-row (Rewaa's own screenshot's row chevron) — another scoped-down simplification, noted so it's not mistaken for an oversight.

"Assign"/"Move" (single row) and the bulk "Assign to category (N)" open `assign-category-dialog.tsx`, a plain category-or-Uncategorized picker; "Create category & assign" (the Uncategorized banner) opens the same `new-category-dialog.tsx` but threads the checked product ids through — the Individual flow passes them as `assignProductIds` on the same `POST /categories` call (one transaction), the Tree flow does a follow-up `PATCH /categories/:id/assign-products` against whichever category the dialog's `parentName` field resolved to. There is no category rename/delete yet (not shown in the reference screens, and delete is genuinely nontrivial with children + assigned products to consider) — only create, list, and (re)assign.


### Products list "..." menu: Import, Bulk Edit, Export

Backend routes are on `ProductsController` alongside the rest (`GET /products/export`, `POST /products/import`, `PATCH /products/bulk-pricing`) — declared *before* `:id` routes so Nest doesn't swallow them. `products-page.tsx` adds row checkboxes (only rendered when the viewer has `products.edit`) feeding all three:
- **Export Products List** (`products.export`) — downloads a CSV of whatever the list's current filters match (not just the current page, capped server-side). Goes through a new `backendDownload()` (`core/api/backend-fetch-client.ts`) rather than `backendFetch()`, since the response is a file, not JSON — this needed the catch-all proxy (`app/api/backend/[...path]/route.ts`) and `backend-fetch-server.ts`'s `callBackend()` to stop unconditionally JSON-wrapping the backend's response body; they now pass a non-JSON `Content-Type`/`Content-Disposition` straight through. Keep this in mind for any future file-download endpoint — it goes through this same path now, not a bespoke Route Handler.
- **Import Products** (`products.create`) — SIMPLE products only, CSV only (matches Rewaa's own reference behavior, which calls out variants/composites as not supported by import either). The template is generated client-side (`utils/import-template.ts`); the result dialog shows a per-row created/error status, since each row is validated exactly like a manual save (`ProductsService.importCsv()` delegates to `create()` per row).
- **Bulk Edit Products Info** (`products.edit`, same permission as a single edit) — select rows on the list, which stashes `{variantId, productId}` pairs in sessionStorage (`utils/bulk-edit-selection.ts` — not the URL, a couple hundred UUIDs would be unwieldy there) and navigates to `/products/bulk-edit`. That page fetches each selected product, lets you pick one location and toggle which fields to edit (price/wholesale/buy price/tax/re-order point), and sends only the fields that actually changed via `PATCH /products/bulk-pricing` — a narrower, purpose-built endpoint, not a loop of the full-product-replacement `PATCH /products/:id` (which would risk clobbering images/options/variants for a change that's only meant to touch prices).

### POS: Registers, Sell Screen, checkout, Invoice List

`features/registers/` (route `/pos`) covers Rewaa's "Registers" screen and the Open/Close Register denomination screens — **not** the Sell Screen (cart, product grid, customer, checkout, pause sale, invoice list). That's a separate, later phase: it touches tax computation, stock decrement, payment recording and invoice numbering all at once, and deserved its own careful pass rather than being rushed alongside Registers. `/pos/registers/[registerId]` (what "Continue Selling" and a freshly-opened register both link to) is the real Sell Screen, built in `features/sales/` — see below.

A `Register` (settings: name, assigned cashiers, payment methods, printer type; `pos.manage_sale_settings` to create/edit) is separate from a `RegisterSession` (one open→close instance; `pos.access` to open/close, and the backend additionally requires the caller be one of the register's assigned cashiers — `registers-page.tsx`'s cards reflect this by disabling Open/Close/Continue Selling for a non-cashier). `pos.manage_cash` gates the Add/Withdraw dialog. The register settings form's four rows (Assigned Cashiers, Payment Methods, Printer Type, Sell Layout) are simplified from the reference screens: Cashiers/Payment Methods open a `Sheet`-based `multi-select-sheet.tsx` (a generic, reusable checkbox-list picker) instead of a nested inline expand; Sell Layout is shown read-only (there's only ever one value, `QUICK_SALE`, so it isn't a real picker). `denomination-form.tsx` (Open Register only) computes the opening amount **from** the denomination counts rather than accepting it as an independently-typed number — more correct for an actual cash count, and a deliberate small deviation from the reference screenshot's two independently-editable fields. **Close Register has its own `close-register-form.tsx`**, not `denomination-form.tsx` — the backend now reconciles every payment method assigned to the register (not just cash), so the close form renders one counted-amount input per non-cash payment method plus the same denomination breakdown for the cash-type one; `RegisterPaymentMethodRef.type` (added alongside this) is how it tells which method is cash.

`MultiSelectSheet`'s draft-reseeding is the render-time "adjust state during render" pattern (`if (open !== wasOpen) { setWasOpen(open); ... }`), not a `useEffect` — the React Compiler lint here (`react-hooks/set-state-in-effect`) forbids synchronous `setState` in an effect body; this is the react.dev-endorsed alternative for "reset state when a prop/condition changes" without an extra render pass.

### Cash Management (`features/cash-management/`, route `/cash-management`)

`pos.manage_cash`-gated, cross-register/cross-location — not scoped to a single register's cashier list the way opening/closing one is. The list (`cash-management-page.tsx`) filters by Location/Register/Status (`OPEN`/`BALANCED`/`UNBALANCED`, both status and the location/register filters are server-side query params, not client-side filtering) and has an Export CSV button. Clicking a row opens `session-detail-sheet.tsx`, a `Sheet` with three locally-tabbed views (not route-based tabs like `SettingsTabs` — this is a single detail record, not navigable sub-pages): **Payment Methods** (expected/counted/difference per payment method plus a Total row — empty with a "still open" message until the session is closed), **Register Summary** (opened/closed by & when, opening amount, totals), and **Add/Withdraw** (read-only history of that session's cash movements, via `listMovementsForSession` which — unlike the Registers feature's own `use-cash-movements-query.ts` — works after the register has closed). The footer's "Session Invoices" opens a dialog listing that session's sales (`useSalesQuery({ registerSessionId })`) reusing `features/sales/components/sale-detail-dialog.tsx` for the per-invoice view; "Print Report" is a plain `window.print()` of the sheet's current tab — a lightweight reconciliation printout, not the customer-facing receipt template (that's a separate, not-yet-built system under Sale Settings → Receipts).

### Sale Settings (`features/sale-settings/`) and Receipt Settings (`features/receipt-settings/`)

Route `/sale-settings`, `pos.manage_sale_settings`, four locally-tabbed sections (not route-based like `SettingsTabs` — one page, `useState` tab, same reasoning as Cash Management's session detail tabs). **Sales** and **Receipts** are real; **Selling Screen** and **eCommerce Orders** are `ComingSoon` (their content wasn't detailed in the reference screenshots, and there's no backend for either).

Both tabs are a **plain `useState` draft object**, not react-hook-form — every field is an independent boolean/enum with no cross-field validation, so there's nothing react-hook-form buys here, and it sidesteps the Controller/reset gotcha (see above) entirely since there's no `reset()` call anywhere. The outer `SaleSettingsPage` fetches and keys each tab's inner component by `settings.updatedAt`, same remount-on-save pattern as Configuration's cards; "Discard" just sets the draft back to the last-saved values (`setDraft(saved)`), no need to actually remount.

The Receipts tab's ~22 checkboxes are grouped Header/Items Content/Footer via `RECEIPT_TOGGLE_SECTIONS` (`features/receipt-settings/types/receipt-settings.ts`) — a frontend-only grouping matching three sections on the entity, not a backend concept. The template selector is a single, disabled "Default" `<Select>`, matching the Sell Layout precedent in Registers (only one value exists, so it isn't a real picker) — flagged to the user as a scoping decision, not silently omitted. The live preview renders the actual `ReceiptDocument` component (see below) against `dummyReceiptSaleData()` — clearly placeholder line items ("Item 1"/"Item 2"), never real transaction data — so the preview is pixel-identical to what a real receipt will look like, not a separate mockup. Comment image upload/remove are their own mutations (`use-comment-image-mutations.ts`) that invalidate immediately, independent of the Save/Discard draft, since the backend commits the upload right away (same as the company logo).

`features/receipt-settings/components/receipt-document.tsx` is the actual printable receipt renderer, shared by all four places that print one: this page's live preview, the Pay dialog's post-checkout screen, and the Invoice List / Session Invoices' `sale-detail-dialog.tsx` Print button (see the printable-receipts note above). It takes `{settings, branding, sale}` — `branding` comes from a new `useCompanyBrandingQuery()` (`features/company/hooks/`, hitting the existing public `GET /company/branding`, now extended with address/phone/VAT/CR fields) so it works for a cashier with no `settings.*` permission at all. `printLayout` only changes the rendered width (THERMAL narrow / A4 wide); every `show*` toggle is a plain conditional render — the component itself has no printing logic beyond `window.print()`, called by whichever screen hosts it.

### Sale Invoices (`/sale-invoices`, `pos.view_sale_invoices`)

`sale-invoices-page.tsx` is the standalone counterpart to the embedded `InvoiceListPage` inside the Sell Screen — same `useSalesQuery()`/filter conventions, but its own Location filter (defaults to "All Locations", not scoped to one register) and an added "Sale Type" filter (`sellAt`: Retail/Wholesale — the only sale-type distinction that actually exists; the reference's Channel and Delivery Partner filters aren't offered since there's no e-commerce/delivery concept in the schema to filter by, a scoping decision flagged here rather than faked with dead dropdowns). Clicking an invoice number or the eye icon navigates to `/sale-invoices/[saleId]` (`invoice-details-page.tsx`) — a real page, not the embedded `SaleDetailDialog`, with the same `ReceiptDocument` preview plus a prominent Print button.

The row-level print icon doesn't navigate anywhere — it renders `AutoPrintReceipt` (`features/receipt-settings/components/`), a headless component that fetches the sale, waits for it plus branding/receipt-settings to load, then calls `window.print()` itself and reports back via `onDone` on the browser's `afterprint` event. Every print call site (this one, the Pay dialog, `sale-detail-dialog.tsx`, Cash Management's Print Report) wraps its printable node in `.receipt-print-area` — a global `@media print` rule in `globals.css` hides everything else on the page for that call, so printing doesn't dump the sidebar/topbar/dialog chrome onto paper alongside the receipt.

### Promotions (`features/promotions/`, route `/promotions`, `pos.manage_promotions`)

**Catalog and scheduling only — nothing here is enforced at checkout** (the Sell Screen/`SalesService` never look a promotion up). This is the same kind of phase boundary as Registers shipping before the Sell Screen did; flagged here so it isn't mistaken for a finished discounting feature.

The list (`promotions-page.tsx`) is an `EmptyState` with a "Create Promotion" button until at least one promotion exists (checked via `total === 0 && status === ALL`, not just `total === 0`, so an empty *filtered* view still shows the ordinary "no results" row instead of the full empty-state illustration); otherwise a table with a Status filter, a Switch per row for the activate/deactivate toggle (`PATCH /promotions/:id/status`), and a delete confirmation dialog. "Create Promotion" goes to `/promotions/new` (`promotion-new-page.tsx`), which shows `PromotionTypePicker` (Discount off Products / Buy X Get Y, two big cards) until a type is chosen, then renders `PromotionFormPage` for that type — no separate route per type, since it's genuinely one creation flow with a type-choice sub-step. Editing (`/promotions/[promotionId]/edit`) reuses the same `PromotionFormPage`, fixed to the saved promotion's type (skips the picker), keyed by `promotion.updatedAt` like every other edit form in this codebase.

`PromotionFormPage` is a large **plain `useState` form**, not react-hook-form — same reasoning as Sale Settings/Receipt Settings (heterogeneous boolean/enum/array fields, no cross-field validation worth react-hook-form's machinery, and it sidesteps the Controller/`reset()` gotcha entirely). It branches on `type` to render either the Discount off Products section (one `TargetPicker` + one `DiscountFields`) or the Buy X Get Y sections (a Buy `TargetPicker` + quantity, a Get `TargetPicker` + quantity + `DiscountFields`) below the shared name/schedule/location fields. `TargetPicker` (`target-picker.tsx`) is reused three times (the Discount flow's target, and the Buy/Get sides) — All Products / Specific Products / Categories, where the latter two open `MultiSelectSheet` (reused from `features/registers/`, a fully generic checkbox-list-with-search picker) fed by a single `useProductsQuery({ pageSize: 200 })` call or `useCategoriesQuery()` — a small, fully-loaded list rather than a server-searched picker, a reasonable size for one restaurant's catalog (same convention as `TablePagination`'s own "small, fully loaded lists" doc comment). `LocationTargeting` is the same All-Locations-toggle-plus-`MultiSelectSheet` pattern for `applyToAllLocations`/`locationIds`.

`ScheduleFields` (`schedule-fields.tsx`) uses native `<input type="datetime-local">` for start/end, converting to/from ISO strings for the API. **The quick-pick buttons (Now/+1 Hour, +1 Day/+1 Week/+1 Month) are a reasonable standard set, not verbatim from the reference screenshot** — the exact button labels weren't legible/available when this was built, flagged in the component's own doc comment so it's easy to swap for the real ones later. The ~22-toggle Receipts-tab precedent (see above) applies here too: expect the user to want some of this adjusted once compared against their actual reference.

`PROMOTION_TARGET_TYPES`/`PROMOTION_DISCOUNT_TYPES`/`PROMOTION_STATUSES` in `types/promotion.ts` mirror the backend's enums exactly (including the derived, not-stored, `status`). Backend permission note: the pickers here needed `GET /products`/`GET /categories`/`GET /locations` to work for a `pos.manage_promotions`-only user with no `products.access`/`settings.locations.manage` — fixed proactively on the backend alongside this feature (see that repo's CLAUDE.md), not discovered later as a bug report.

### Expenses (`features/expenses/`, route `/expenses`, `expenses.access`/`create`/`edit`/`delete`)

Plain CRUD list matching the other simple-entity features (Customers, Promotions): filters (date range, category), a table, an `ExpenseDialog` for add/edit keyed by `expense?.id ?? 'new'` (create vs. edit reuse the same dialog component, so it must remount on target change — same keyed-remount rule as every other form in this codebase), and a delete confirmation dialog. `EXPENSE_CATEGORIES` (`RENT | SALARIES | UTILITIES | OTHER`) mirrors the backend's fixed enum — there's no "manage categories" screen, matching the backend's own scoping note.

### Dashboard (Home, `features/dashboard/`) and Reports (`features/reports/`, route `/reports`, `reports.access`)

Both were built to match two reference screenshots pixel-for-pixel in *structure* (stat cards, a sales chart, breakdowns, a profit/expenses panel), while the Rewaa-specific SaaS chrome in those screenshots — the "Trial version" banner, the gift/theme icons, a global branch switcher in the topbar — was deliberately **not** replicated: this is a single-tenant, self-hosted app (no subscription/billing concept, already called out elsewhere in this doc for Settings), and a global topbar location switcher would be a bigger architectural change than either page actually needed. Instead each page has its own local location `<Select>` (only rendered when there's more than one location at all), passed straight through as `locationId` to its one query.

**No charting library was added** — `src/components/charts/` (`LineAreaChart`, `BarChart`, `DonutChart`, `HorizontalBarChart`) are small, dependency-free SVG/flexbox components, matching this codebase's established "hand-roll it" convention (CSV, date math) rather than pulling in recharts/chart.js for four chart shapes. `DonutChart` computes its cumulative arc offsets as two pure `.map()` passes, not a mutated loop variable across the JSX-returning map — the first version did that and the React Compiler's immutability lint rejected it (`Cannot reassign variable after render completes`); worth remembering for any future chart that needs a running total.

**Home (`/`) has no permission gate of its own** — unlike every other page, it can't `requirePermission()` and redirect away on a miss, since that would redirect `/` to itself. `page.tsx` instead branches server-side on whether the session has `dashboard.access`: if not, it renders `WelcomeQuickLinks` (the original simple "Welcome back" + permission-filtered quick-links cards, extracted unchanged into its own component) instead of `DashboardPage` — so a Cashier role with no `dashboard.*` permission still lands on a working Home page instead of a 403 or an empty shell. `DashboardPage` itself further trims which of its sections render via `usePermission()` checks matching the backend's `DashboardViewer` trimming (`dashboard.view_financial_metrics`/`sales_breakdowns`/`sales_insights`/`view_register_insights`) — if a query's `financials`/`salesBreakdown`/etc. comes back `null` (no permission) the corresponding card just doesn't render, rather than crashing on a null dereference.

Reports' "Best-selling products" Export CSV button doesn't hit a new backend endpoint — the full `bestSellingProducts` array is already in the page's one `GET /reports` response, so it's built client-side with the existing `toCsvRow` (`src/lib/csv.ts`) + `downloadBlob` helpers, same pattern as the product-import template generator.

### Purchases & Suppliers (`features/suppliers/`, `features/purchase-invoices/`, `features/return-invoices/`, `features/supplier-payments/`)

Four features mirroring the backend's four modules 1:1. `SuppliersPage` is a plain CRUD list (add/edit dialog keyed by `supplier?.id ?? 'new'`, same rule as Expenses/Promotions) plus a derived `balance` column and a "Deactivate" action instead of delete (a supplier with purchase history can't be hard-deleted — see the backend CLAUDE.md).

`PurchaseInvoiceFormPage`/`ReturnInvoiceFormPage` are near-identical line-item editors: a header (Supplier/Location/Date/Notes) plus a searchable product picker (`useProductsQuery` with a debounced search term, matching the `TargetPicker`-style "small dropdown of live search results" pattern) that adds a row per product, each row directly editable (quantity/unit cost/tax). The whole form is wrapped in `<fieldset disabled={!isEditable}>` where `isEditable = status === 'DRAFT'` — a confirmed invoice renders the identical form read-only rather than a separate view page, same convention as Tax's `SYSTEM_LOCKED`/`SYSTEM_TOGGLABLE` read-only guard. There's no separate `/purchase-invoices/[id]` view route, only `/purchase-invoices/[id]/edit`, since the form itself already handles both modes.

**"Save & Confirm" needs two different request shapes depending on create vs. edit** — a real gotcha worth remembering: `POST /purchase-invoices` accepts `status: 'CONFIRMED'` directly (confirming a brand-new invoice in one call), but `PATCH /purchase-invoices/:id` doesn't accept `status` at all (the backend's `UpdatePurchaseInvoiceDto` omits it via `OmitType`, and the global `ValidationPipe` has `forbidNonWhitelisted: true` — sending it anyway 400s). So `handleSave()` branches: creating a new invoice passes `status` inline; editing an existing draft calls `update()` (no status) and, only if the user chose "confirm," chains a separate `confirm()` mutation after it succeeds. Same pattern in both `purchase-invoice-form-page.tsx` and `return-invoice-form-page.tsx`.

`SupplierPaymentsPage`'s "Total Outstanding" card sums every supplier's derived `balance` from `useSuppliersQuery()` (already fetched for the filter dropdown) rather than a separate aggregation call — the data's already in hand. Creating or deleting a payment invalidates `suppliersKeys.lists()` alongside its own query key, since a payment changes every affected supplier's derived balance.

### Stock (`features/stock-operations/`, `features/stock-count/`, `features/stock-transfer/`)

Three independent features mirroring the backend's three modules 1:1 (`stock.access`/`record_draft`/`manage_movements`/`manage_counts`/`request_transfer`/`approve_transfer`), none sharing state with each other. `core/auth/permissions.ts` gained a new `requireAnyPermission()` server helper alongside the existing `requirePermission()` for this — Stock Operations' create/edit route needs an "any of" check (`stock.record_draft` OR `stock.manage_movements`, mirroring the backend's `@RequireAnyPermission`) that the all-of-only `requirePermission()` couldn't express; use it for any future page gated the same way.

**Stock Operations** (`/stock-operations`, list + `/new` + `/[id]/edit`) is built exactly like Purchase Invoices: a searchable product picker adds line rows (quantity only — no cost/tax, since a stock movement doesn't touch cost), `<fieldset disabled={!isEditable}>` where `isEditable = status === 'DRAFT'`, and the same two-request-shape "Save & Confirm" gotcha as Purchase/Return Invoices (`create()` accepts `status` inline, `update()` never does — confirm is a separate chained mutation on an existing draft). The product search uses `useProductsQuery({ ..., excludeComposite: true })` rather than filtering results client-side — a composite has no stock of its own to move, and the backend would reject it anyway.

**Stock Count** (`/stock-count` list + `/[id]` detail — no `/new` route; creating one is a small dialog right on the list page since it only needs a Location + Count Date, not a full form) has no product picker at all — `create()` auto-populates every line server-side from what's already stocked at that location, so the detail page (`stock-count-detail-page.tsx`) just renders one row per pre-populated line with an editable "Counted Quantity" input (blank = not yet counted, matches the backend's "leave uncounted lines untouched on confirm" rule) and a "Save Counts" button that only sends lines the counter actually typed a value into (`PATCH .../:id/lines`), plus a separate "Confirm Count" button.

**Stock Transfer** (`/stock-transfer` list + `/new` + `/[id]` detail — no edit route; there's no `DRAFT` state to edit, a transfer is live the moment it's requested) is a request/approval flow, not a draft/confirm one: `/new` is a From/To location picker plus the same product-picker line-item pattern as Stock Operations (quantity only), gated `stock.request_transfer`. The detail page's action row is genuinely three-way conditional — `useSession().id === transfer.requestedByUserId` (not just a permission check) decides whether "Cancel Request" shows at all, separately from whether `stock.approve_transfer` unlocks Approve/Reject, so a cashier who requested a transfer sees Cancel but never Approve/Reject on their own request, matching the backend's identical requester-vs-approver split. List rows have no inline dropdown of actions (unlike Purchase Invoices' per-row menu) — the From Location cell just links to the detail page, and every action (Cancel/Approve/Reject) lives there instead.

`features/customers/` (route `/customers`, `customers.access`/`create`/`edit`/`delete`/`export`) — a full CRUD matching the reference screens: list (search, Export CSV, pagination) and a Customer Details form (personal info, phone via the shared `core/phone/country-codes.ts` split, KSA VAT number format validated client- and server-side, address block). "Custom Fields" and "Set Opening Balance" are shown as disabled, clearly-labeled "coming soon" sections (no custom-fields system or accounting ledger exists yet) rather than omitted outright, matching the Item Source precedent in the product form. `Total Paid`/`Debit Amount` are now real (see Customer Payments below), derived server-side — this page doesn't compute anything itself, `customer.totalPaid`/`customer.debitAmount` just come back populated from `GET /customers` now. The Country field is a plain text input pre-filled "Saudi Arabia", not a full country picker (only one country was ever shown selected in the reference).

### Customer Payments (`features/customer-payments/`, route `/customer-payments`, `customers.view_balances`/`manage_settlements`)

Mirrors Supplier Payments' shape (a list + a "Record Payment" dialog, a "Total Outstanding" card, `paymentDate`/`amount`/`paymentMethodId`/`notes`) with one structural difference: **Suppliers is a small, fully-loaded list** (`useSuppliersQuery()` with no pagination, so its dialog's supplier picker and its outstanding-total card both just use that one already-fetched array) — **Customers is genuinely paginated** and can be large, so neither of those tricks works here. Instead: `customer-payment-dialog.tsx`'s customer picker and the list page's `customer-filter-search.tsx` are both live-search comboboxes over `useCustomerSearchQuery()` (the same narrow, capped `GET /customers/search` the POS "Add Customer" flow already uses), and the "Total Outstanding" card reads `useReceivablesSummaryQuery()` — a dedicated one-query backend aggregate (`GET /customers/receivables-summary`) — instead of summing a full customer list that was never fetched. Once a customer is picked in the record-payment dialog, `useCustomerQuery(id)` (`GET /customers/:id`, now returning `totalPaid`/`debitAmount` too) shows their current outstanding balance inline before the amount is entered, so whoever's recording the payment can see what's actually owed.

A payment is a plain settlement against the customer's account balance, not allocated to a specific sale — same account-level scope decision as Supplier Payments (a per-sale payment-allocation ledger would be a much larger feature). Creating or deleting a payment invalidates `customersKeys.all` (list, detail, *and* the receivables summary all live under that one key prefix) alongside its own query key, since a payment changes the customer's derived balance everywhere it's shown.

**"Pay Later" checkout** (`features/sales/components/pay-dialog.tsx`) is what actually puts money on a customer's balance in the first place — without it, nothing could ever be owed, since an ordinary sale is always paid in full at checkout. Gated by `pos.checkout_post_payment` and only shown at all once a customer is selected in the Sell Screen (billing "nobody" makes no sense), it's a toggle that — when on — hides the Payment Method buttons and Amount Tendered input entirely and shows a one-line explainer instead; `handleComplete()` then sends `isPostPayment: true` with `paymentMethodId`/`amountTendered` omitted. `CheckoutSaleInput.paymentMethodId`/`amountTendered` are consequently optional now (previously required) — every other call site (the Pay dialog's own normal-payment branch) is unaffected since it always supplies both. Checkout still resolves everything server-side exactly as before (stock, tax, totals); only the payment step changes. `useCheckoutSaleMutation` additionally invalidates `customersKeys.all` when `variables.isPostPayment` is set. Wherever a completed sale's payment method name is displayed and comes back empty (`invoice-list-page.tsx`, `sale-invoices-page.tsx`, `receipt-document.tsx`) it now falls back to "Pay Later" — the only thing a null `paymentMethodId` can mean on a COMPLETED sale, since payment methods themselves are never deletable (see Payment Methods, above).

### Sell Screen, checkout, Invoice List (`features/sales/`)

The Sell Screen (`sell-screen.tsx`) is a client-only cart (`CartLine[]` in local state) until the cashier pays or pauses — nothing is persisted per keystroke. Browsing reuses the *existing* `GET /products` (and `GET /categories`) endpoints as-is (search/category/pagination all already built for the admin Products list) rather than a new POS-specific catalog read — those two routes (plus `GET /products/form-options`) are gated `@RequireAnyPermission('products.access', 'pos.access')` on the backend specifically so a Cashier role with `pos.access` and no `products.*` permissions can still use them (this 403'd before it was fixed — a Cashier test user hit "Something went wrong" on `/pos` because of it); rows are variants, same convention as the admin list, so a VARIABLE product's variants each show as their own grid card. This means the grid's displayed price/stock reflects the **default location**, not necessarily the register's own location in a multi-location setup — a deliberate v1 simplification, safe because checkout always re-resolves the true price/tax/stock from the register's actual location server-side and never trusts what was on-screen.

**The cart's running total is never computed client-side.** The footer shows a plain, always-exact `Subtotal` (Σ unitPrice×qty, no tax). Opening `pay-dialog.tsx` calls `POST /sales/park` immediately to get the server's authoritative subtotal/discount/tax/total breakdown, displayed there for the actual payment step — the one place precision genuinely matters. "Complete Sale" then calls `POST /sales/checkout` with `resumedFromSaleId` set to that same parked row, so pay-dialog's preview and the final charge are always the same underlying record. "Pause Sale" is the same `park()` call without the payment step; "Continue Sale" (shown when the cart is empty) opens `parked-sales-dialog.tsx`, and resuming rehydrates the cart **directly from the parked sale's own snapshotted line data** (`productName`/`sku`/`unitPrice`) — no re-fetch of the product catalog needed, and prices stay exactly as parked even if the catalog price changed meanwhile.

**Printable receipts** (previously a flagged gap — now resolved): after `handleComplete()` succeeds, `pay-dialog.tsx` no longer closes immediately — it shows a receipt/print screen (`ReceiptDocument` from `features/receipt-settings/`) with Print (`window.print()`) and Done buttons; `onCompleted(sale)` (which resets the cart) still fires right away, only the dialog stays open. That receipt is built by `checkoutToReceiptData()` straight from data the cashier already has in hand — the checkout response, the cart's own `CartLine[]`, the chosen payment method's name, `useDisplayName()` for the cashier, and a `customerName` prop threaded down from `sell-screen.tsx`'s already-selected `Customer` — deliberately **not** a `GET /sales/:id` re-fetch, since that route needs `pos.view_sale_invoices`/`pos.manage_cash` and an ordinary cashier printing their own just-completed sale shouldn't need either. `sale-detail-dialog.tsx` (used by the POS Invoice List tab and Cash Management's Session Invoices) gets the same Print button, but via `saleDetailToReceiptData()` instead, since there a real `GET /sales/:id` fetch already happened and has `cashierName`/`customerName`/`paymentMethodName` from the backend directly.

`pay-dialog.tsx`'s open/close effect follows the same react.dev "adjust state during render" pattern as `MultiSelectSheet` (see Registers, above) for the reset-on-close part; the actual `park()` network call stays in a `useEffect` keyed on `open` (a real external side effect, not a synchronous setState, so it doesn't trip the same lint rule).

Permission-gated UI, each backed by a matching server-side re-check in `SalesService` (never trust the client): `pos.sell_wholesale` for the Retail/Wholesale toggle (hidden entirely without it), `pos.edit_prices_discounts` for Note/Discount, `pos.remove_cart_items` for the per-line trash icon, `pos.park_sale` for Pause/Continue Sale, `pos.view_sale_invoices` for the Invoice List tab. "Add" (a label in the reference cart footer next to Note/Discount) was left out — its purpose wasn't identifiable from the screenshots, and it seemed better to omit than guess.

Invoice List (`invoice-list-page.tsx`) reuses `usePaymentMethodsQuery`/`useLocationsQuery` for its filter dropdowns; there's no "Serial Number" filter (nothing in this app tracks serials) and only one "Type" (Sale — Return Invoices isn't built). Row actions are just a "View" that opens `sale-detail-dialog.tsx` (a read-only line-item + totals breakdown, not a printable receipt).

### Accounting — full double-entry (`features/chart-of-accounts/`, `features/journal-entries/`, `features/fixed-assets/`, `features/financial-reports/`, `features/accounting-overview/`)

Four routes under the sidebar's Accounting group, plus a fifth (`/financial-reports`) added to `nav-config.ts` that wasn't in the original coming-soon scaffolding — `accounting.view_financial_reports` existed in the permission catalog with nowhere to point yet. **Scope note**: nothing elsewhere in this app (Sales, Purchases, Expenses, Payments) posts to this ledger automatically — every journal entry is manual, or comes from a Fixed Asset's purchase/depreciation posting. See the backend CLAUDE.md for why that's a deliberate v1 boundary, not an oversight.

**Chart of Accounts** (`/chart-of-accounts`, `accounting.manage_chart_of_accounts` gates the whole route — same "nav-permission gates the page" convention as `/category-management`) renders as a small, fully-loaded list like Suppliers (`useAccountsQuery()`, no pagination), grouped into five sections by `type` (Assets/Liabilities/Equity/Revenue/Expenses) rather than a nested parent/child tree — simpler and matches how a real chart of accounts is conventionally read. A system account (lock icon next to its name) has no Deactivate/Delete option in its row menu, mirroring Tax's `SYSTEM_LOCKED` precedent exactly.

**Journal Entries** (`/journal-entries` list, `/journal-entries/new`, `/journal-entries/[id]/edit` for a DRAFT, `/journal-entries/[id]` for a POSTED entry) is the one place in this app with **two separate routes for edit vs. view** instead of one `<fieldset disabled>` form (the Purchase Invoice precedent) — a posted entry's only available action is Reverse, fundamentally different from a draft's Save/Post, so it gets its own read-only detail page (`journal-entry-detail-page.tsx`) rather than a disabled copy of the edit form. `journal-entry-edit-page.tsx` guards against a stale `/edit` link to an entry that's since been posted (e.g. a second tab) by redirecting to the view route client-side (`useEffect` + `router.replace`, not a render-time `redirect()` call, to keep the render pure) rather than rendering a disabled form nobody asked for. The line-entry table's debit/credit inputs are **mutually exclusive per row** (typing in one clears the other) with a live-computed Σdebit/Σcredit balance indicator (green when equal, red otherwise) — "Save & Post" is disabled until it balances, matching the backend's own validation so the error is never a surprise after clicking. `create()` never takes a create-with-status shortcut (unlike Purchase Invoices) — it's always DRAFT first, `post()` is a always separate follow-up call, matching the backend's own "build it up, then post" design for a manual entry.

**Fixed Assets** (`/fixed-assets`, `accounting.manage_fixed_assets`) is a single list + dialogs (create/edit, Record Depreciation, Dispose) — no dedicated detail page, since everything worth showing (accumulated depreciation, book value) already fits in the list's own columns. The create dialog's three account pickers are pre-filtered by type (`useAccountsQuery({ type: 'ASSET' })` for the asset/accumulated-depreciation pickers, `{ type: 'EXPENSE' })` for the depreciation-expense one) so the dropdown can't offer a nonsensical combination. "Paid From" (`paymentAccountId`) only appears on create, not edit — matches the backend's `UpdateFixedAssetDto` omitting `purchaseCost`/`purchaseDate`/`paymentAccountId` entirely, since editing an asset after depreciation has already posted against it can't retroactively touch the purchase accounting. Delete is only offered when `accumulatedDepreciation === 0` (client-side convenience matching the backend's own "has depreciation entries" guard) rather than always showing a delete option that would just 400.

**Financial Reports** (`/financial-reports`, `accounting.view_financial_reports`) is four locally-tabbed reports (Trial Balance / General Ledger / Income Statement / Balance Sheet — same `useState` local-tab pattern as Sale Settings/Cash Management's session detail, not route-based tabs) each a thin presentational wrapper around one backend aggregate endpoint; there's no client-side computation beyond currency formatting. General Ledger requires picking an account first (a live search-free `<Select>` over the small Chart of Accounts list) before it fires its query at all — `enabled: Boolean(accountId)` on the hook, showing an explicit "select an account" empty state rather than an empty table.

**Setup Guide** (`/setup-guide`, `accounting.view_setup_guide`) is a small overview page — three link-cards (Chart of Accounts / Journal Entries / Fixed Assets) each showing real counts from `GET /accounting/setup-guide`, plus a trial-balance-balanced banner — deliberately not a checklist with fake "done" checkmarks for steps that can't actually be verified (see the backend CLAUDE.md's identical reasoning). Lives in its own small `features/accounting-overview/` rather than inside `features/chart-of-accounts/`, since it isn't really about the chart of accounts specifically, just happens to be served by that module's controller on the backend.

### Digital Menu (`features/digital-menu/`, public route `/menu`, internal admin route `/digital-menu`)

**The one route in this codebase that's genuinely public** — no session, no `requirePermission()`, reachable by a customer who's never logged in. `proxy.ts` needed a real change for this: its existing `PUBLIC_PATHS` list (`/login`, `/accept-invitation`, `/forgot-password`) redirects an *already-authenticated* visitor away to `/` — exactly wrong for `/menu`, where a manager checking what customers see should be able to view it normally without getting bounced. The list was split in two: `AUTH_ONLY_PUBLIC_PATHS` (the original three, keeps the redirect-if-already-signed-in behavior) and a new `PUBLIC_PATHS` (`/menu`) that's public but never redirects on session state either way.

`/menu/page.tsx` is a genuine **Server Component** — the only page in this app that doesn't fetch through TanStack Query + the authenticated catch-all proxy. It calls `core/digital-menu/get-digital-menu.ts`'s `getDigitalMenu()`/`getDigitalMenuLocations()` directly, following the exact same narrow, documented exception as `core/company/get-company-branding.ts` (`callBackend()` straight from a server context, no cookies needed since the backend routes are `@Public()`). This buys a real SEO title/description (`generateMetadata()`) and zero loading-spinner flash on a phone scanning a QR code on possibly-slow data — worth the one-off deviation from this app's otherwise-universal client-fetch convention, precisely because this page has no session to seed a client-side provider with in the first place.

`digital-menu-view.tsx` (client component, receives the server-fetched data as props) is the actual menu UI: a sticky branded header (logo/name/address-phone, a location `<Select>` shown only when there's more than one active location — switching pushes `?locationId=` and lets the Server Component refetch), a live client-side search filter, and a horizontal category pill nav. Category nesting is deliberately flattened to 2 levels for the nav (`features/digital-menu/utils/category-tree.ts`'s own small tree-builder, not reused from Category Management since the shapes differ) — selecting a top-level pill shows its own products plus every descendant category's, via `categoryAndDescendantIds()`. `menu-product-card.tsx` shows the image (plain `<img>`, external Firebase URL, same eslint-disable convention as `receipt-document.tsx`) or a placeholder icon, name, description, and either a single price / price range or a per-variant price list for a VARIABLE product with more than one priced variant — an all-variants-out-of-stock product gets a "Sold Out" overlay on its image rather than disappearing, matching the backend's same "still show it" philosophy.

**Internal admin preview** (`/digital-menu`, `pos.manage_digital_menu` — this permission and nav entry already existed, pointing at a coming-soon stub) is deliberately *not* a settings/configuration screen — there's no menu-specific data to configure (no featured items, no custom sort order; see the backend CLAUDE.md's note on that). Instead `digital-menu-admin-page.tsx` reuses the exact same `DigitalMenuView` component for a live, authenticated preview (fetched via the normal `backendFetch()`/TanStack Query path this time, since it's inside the dashboard), plus a location switcher backed by the full `useLocationsQuery()` (not the public narrow one — an already-authenticated staff member can just use the real list), and "Copy Link"/"Open Public Menu" actions. Both actions compute `window.location.origin` lazily **inside their click handlers**, never in the render body or an effect — reading it in render would mismatch the server-rendered HTML on hydration (no `window` during SSR), and stashing it in state via `useEffect` would trip the React Compiler's `set-state-in-effect` lint (see the Registers/`MultiSelectSheet` precedent above) for no real benefit, since nothing here needs to render differently before that value is known. The embedded preview is passed `locations={[]}` to suppress its own built-in location switcher, which would otherwise navigate to the public `/menu` route — wrong from inside this admin page, since the switcher above it already covers that.
